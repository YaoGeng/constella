# 扩展能力分层调研：Codex 类能力能否进星丛（MCP/插件/命令/agent/skill/模型设置/操作电脑/Office/HTML）

- 调研日期：2026-11-08（取证访问日）
- 性质：docs/research/ 证据文件；第八章为编排者对照已封版架构（00 v1.2 / 01 v1.0 / 02 v1.0）的决策建议，**非取证内容**
- 结论速览：**全部能力技术可行**；分层判据 =「执行与安全 → 应用本体；可组合计算/IO 单元 → 节点；知识/流程/prompt → 文件级用户内容（本体 loader 加载）」；建议本体强化内核、节点强化表面（业界 C+B 混合），V1 封版不动，新增能力走 00 H 章变更流程进 V1.x/V2

## 第一章 OpenAI Codex（CLI + IDE + 云端 agent）

### 1.1 平台内置 vs 用户可扩展的边界

**平台内置（本体）**：
- 沙箱与审批：`sandbox_mode` 三档（`read-only` / `workspace-write` / `danger-full-access`），macOS 用系统内置 Seatbelt 框架开箱即用，Windows 用原生 Windows sandbox，Linux 为 Landlock（+seccomp/Bubblewrap，Landlock 路径在有 Bubblewrap 时属旧路径——此细节来自第三方与 GitHub issue，官方页本次未读全文）；强制失败即拒绝执行而非放行。来源：Codex config reference（learn.chatgpt.com/docs/config-file/config-reference）、官方 sandboxing 文档（learn.chatgpt.com/docs/sandboxing）、第三方佐证 Agent37 2026、GitHub issue #7657
- 审批策略：`approval_policy` 支持细粒度对象（`sandbox_approval`、`rules`、`mcp_elicitations`、`skill_approval`），`untrusted` 不再支持、`on-failure` 已弃用；企业可用 `requirements.toml` 设 `allow_managed_hooks_only = true` 只保留托管 hooks
- Computer Use（见第五章）：平台内置，桌面端逐应用授权，管理员可用 `[features].computer_use = false` 关闭
- Skills loader：平台内核负责扫描、渐进披露、上下文预算控制

**用户可扩展（文件级）**：
- `~/.codex/config.toml`（用户级）与 `.codex/config.toml`（受信项目级）：模型选择（如 gpt-6.1-sol）、`model_providers`（内置保留 id：openai/ollama/lmstudio，另有 amazon-bedrock、gcp 内置块）、`model_reasoning_effort`（low/medium/high/xhigh/max/ultra，随模型而定）、profiles（`$CODEX_HOME/<profile>.config.toml`）、`windows.sandbox`（mxc/elevated/unelevated）
- AGENTS.md：`/init` 生成，分层指令文件
- 自定义 prompts：`~/.codex/prompts/*.md` → `/prompts:name` 斜杠命令，带 `$1..$9`、`$ARGUMENTS`、命名占位符——**官方已标注「Deprecated. Use skills for reusable prompts」**（learn.chatgpt.com/docs/custom-prompts；弃用后有 issue #15941 反映不显示）
- MCP servers：见 1.2

### 1.2 MCP：客户端完整、服务端已移除

- 客户端：`codex mcp add <name> -- <cmd>`（stdio）或 `codex mcp add <name> --url ... --oauth-client-id ...`（HTTP，支持 OAuth 含 CIMD 与 DCR）；`codex mcp login/list`；TUI 内 `/mcp` 查看。config.toml `[mcp_servers.<name>]` 定义 command/args/env/url/headers、`startup_timeout_sec`（默认10s）、`tool_timeout_sec`（默认60s）；工具级 `enabled_tools`/`disabled_tools`/`tools.<tool>.approval_mode`（auto/prompt/writes/approve）/`output_token_limit`。来源：learn.chatgpt.com/docs/extend/mcp
- **「Codex 作为 MCP server」已删除**：官方页明言「The codex mcp-server command and the standalone codex-mcp-server binary have been removed」，替代物是实验性的 Codex app server（自有 JSON-RPC 协议，「isn't an MCP server or a drop-in replacement for an MCP client」，不支持生产）。来源：learn.chatgpt.com/docs/mcp-server。第三方教程仍在写 `codex mcp serve`，与官方现文档冲突——**以官方为准：现版本不提供 MCP server 模式**。
- 跨端共享：「The ChatGPT desktop app, Codex CLI, and IDE extension support MCP servers and share MCP configuration for the same Codex host」；ChatGPT 网页端不读本地配置，走远程插件。

### 1.3 Skills：平台 loader + 用户文件（与 Claude Code 同一开放标准）

- 定义：目录 + `SKILL.md`（name/description 必填）+ 可选 `scripts/`、`references/`、`assets/`、`agents/openai.yaml`（UI 元数据、调用策略、工具依赖）；「Skills build on the open agent skills standard」（agentskills.io）
- 扫描目录：仓库 `.agents/skills`（向上至 repo 根）、`$HOME/.agents/skills`、`/etc/codex/skills`（管理员）、系统捆绑（skill-creator、skill-installer）
- 渐进披露：启动只载 name+description，决定使用才载全文；初始清单约上限为上下文的 2%（未知则 8000 字符），`skills.max_context_tokens` 最高 10000
- 调用：显式 `$skill-name` / `/skills`，或模型按 description 隐式调用（`allow_implicit_invocation: false` 可关）
- 配置与分发：`~/.codex/config.toml` 中 `[[skills.config]]` 逐项启停；分发走 plugins（可捆绑 skills + MCP connectors）
- 来源：learn.chatgpt.com/docs/build-skills

分层判定：**Codex 把「加载机制、上下文预算、审批」放本体，把「skill 内容、prompt、MCP server、AGENTS.md」全部放用户文件——典型 C 模式**。

## 第二章 Claude Code / 编码 agent 的三层分工

### 2.1 Skill / Subagent / Command（+Hook）职责与加载机制

- **Skill**（用户内容，平台 loader）：目录 + `SKILL.md`（frontmatter：`description`、`name`、`argument-hint`、`disable-model-invocation`、`user-invocable`、`allowed-tools`、`context: fork`、`model`、`paths`；正文 markdown；支持 `` !`command` `` 动态注入）。渐进披露三级：描述常驻上下文 → 调用才载全文 → 按需读附属文件。位置：`~/.claude/skills`（个人）、`.claude/skills`（项目，可提交）、企业托管目录、插件目录、claude.ai 同步。**官方明确「Custom commands have been merged into skills」**：`.claude/commands/deploy.md` 与 `.claude/skills/deploy/SKILL.md` 产生同一 `/deploy`，旧格式仍兼容。内置捆绑 skills：`/doctor`、`/code-review`、`/batch`、`/debug`、`/loop` 等，可被同名自定义覆盖。来源：code.claude.com/docs/en/skills
- **Subagent**（用户内容，平台调度器）：markdown + YAML frontmatter，必填仅 `name`/`description`；可选 `tools`、`model`、`permissionMode`、`maxTurns`、`mcpServers`、`hooks`、`skills`、`memory`、`effort`、`isolation: worktree`、`background`、`omitClaudeMd` 等。**每个 subagent 独立上下文窗口**，系统提示=正文；调用从自然语言委托 → `@agent` 强制 → `claude --agent` 全会话；可并行（默认并发上限 20）、可嵌套至三层（可配置）；所有 agent 的 description 合计超 15,000 token 会告警。来源：code.claude.com/docs/en/sub-agents
- **Hook**（用户内容，平台事件总线）：五种 handler（`command`/`http`/`mcp_tool`/`prompt`/`agent`）挂在生命周期事件上（SessionStart/End、UserPromptSubmit、Stop、PreToolUse/PostToolUse、PermissionRequest/Denied、SubagentStart/Stop、PreCompact 等）；exit code 2 阻断动作；可改写工具入参/出参、注入上下文；管理员可 `allowManagedHooksOnly`。官方提醒：if 过滤是尽力而为，「use the permission system rather than a hook to enforce a hard allow or deny」。来源：code.claude.com/docs/en/hooks
- **三层分工总结**：skill=「知识/流程注入主上下文，渐进披露」；subagent=「隔离上下文的专用执行体，平台调度并行」；command=「skill 的用户显式入口（已合并）」；hook=「宿主生命周期上的确定性守护」。平台内核提供：loader/调度/事件总线/权限系统/上下文管理——**这些全是平台能力；三层内容全是用户 markdown/json 文件**。

### 2.2 MCP（host 角色）与模型设置

- MCP：Claude Code 是 host/client。`.mcp.json`（项目根，`{"mcpServers": {...}}`，支持 `${VAR}` 展开）；三作用域（local 存 `~/.claude.json` / project 提交入库 / user 跨项目），优先级 local > project > user > plugin > claude.ai connectors；`claude mcp add --transport stdio|http|sse`（SSE 已弃用，http 推荐）；OAuth 2.0（token 安全存储自动刷新、`headersHelper` 动态 token、防凭据泄漏展开）；安全实践：「prompts for approval … before using project-scoped servers」、拒绝清单 `disabledMcpjsonServers`、MCP 工具命名 `mcp__<server>__<tool>`、输出默认 25,000 token 上限、超 2 分钟工具调用自动转后台。SDK 宿主应用可注册进程内 `"type": "sdk"` server。来源：code.claude.com/docs/en/mcp
- 模型设置：`settings.json` 四层（user / project / local / managed），优先级「Managed settings, command line, project local, shared project, user」；安全敏感键低层更严者胜出；`permissions.allow/ask/deny` 规则；`model` 键仅会话启动读取，中途 `/model`；托管 `model` 是默认值非锁，真正的锁是 `availableModels`/`deniedModels`。来源：code.claude.com/docs/en/settings
- 插件：一个目录打包 skills+agents+hooks+MCP servers（+mods：可绘面板的 JS 模块），manifest 在 `.claude-plugin/plugin.json`；marketplace=带 `marketplace.json` 的仓库，「a catalog, not a hosted store」；三层在场（settings 声明+磁盘+会话）才生效；「what the plugin runs, it runs as you」。来源：code.claude.com/docs/en/plugins
- Agent SDK（平台内核的商品化出口）：「a library that runs the Claude Code binary」，提供「the same tools, agent loop, and context management that power Claude Code」，含 hooks/subagents/MCP/permissions/sessions/skills/commands/memory/plugins。来源：code.claude.com/docs/en/agent-sdk/overview
- Computer Use：Claude Code 内置一个名为 `computer-use` 的 **MCP server**（默认关闭）：可「open apps, click, type, scroll, and take screenshots」；macOS 研究预览；需 Accessibility+Screen Recording 权限；逐会话逐应用审批（终端/IDE 标注「Equivalent to shell access」，浏览器/交易平台 view-only，终端 click-only）；Esc 随时中止。来源：code.claude.com/docs/en/computer-use。**这是「平台内置能力借用 MCP 扩展点协议实现」的直接证据。**

## 第三章 n8n 与 ComfyUI：节点生态的边界

### 3.1 n8n

- **官方节点 vs 社区节点的边界**：官方/内置节点随 n8n 主包分发；社区节点是 npm 包（命名必须 `n8n-nodes-*` 或 `@<scope>/n8n-nodes-*`，package.json `n8n` 属性注册节点与凭据）。安装四途径：节点面板（**仅 verified**）、应用内 GUI 装 npm 包、命令行、环境变量引导。**未验证节点只能自托管**。verified 审核：Creator Portal 提交、最长四周、「verified nodes aren't allowed to use any run-time dependencies」、2026-05-01 起必须 GitHub Actions + provenance 发布；与 n8n 付费/企业功能竞争的节点可能被拒。另有风险说明与封禁清单专页。来源：docs.n8n.io/integrations/community-nodes/installation-and-management.md、building-community-nodes.md
- **参数 schema 声明（与节点 UI 的关系）**：两种建法——声明式（默认推荐，JSON-based syntax，无需 `execute()`，参数以 `properties` 数组 JSON 声明，n8n 据此**自动渲染节点 UI**，`displayOptions.show` 控制显隐）与程序式（`execute()` 自行取参构请求；trigger 节点必须程序式）。来源：docs.n8n.io/connect/create-nodes/plan-your-node/choose-a-node-building-style.md。**UI 引擎与执行引擎在本体，节点只交声明**——与星丛 N3 schema DSL + ParamFormRenderer 同构。
- **MCP 与 AI Agent 节点的定位**：都是**平台官方内置（core nodes，`n8n-nodes-langchain.*` 家族）**，不是社区节点：
  - MCP Client 节点：「use MCP tools as regular steps in a workflow」；配 transport、Endpoint URL、认证；**「The list of tools is automatically fetched from the external MCP server」**——选工具走下拉，参数用 Input Mode 手填或 JSON
  - MCP Client Tool 子节点：把 MCP server 的一组工具挂给 AI Agent
  - MCP Server Trigger：让 n8n 本身当 MCP server，「making n8n tools and workflows available to MCP clients」；传输 SSE 与 streamable HTTP、**不支持 stdio**；可用 Custom n8n Workflow Tool 把整个 workflow 暴露为工具
  - AI Agent 节点：root node，LangChain 基座；「You must connect at least one tool sub-node」；模型/记忆/工具/输出解析器都是子节点
- 分层判定：**n8n 把 MCP/AI 能力做成「平台内置节点」，同时保持节点形态与子节点插槽协议不变——即新能力进入平台时仍以生态统一单元（节点）表达，而不是另起插件体系。**

### 3.2 ComfyUI

- Custom node 机制：`custom_nodes/` 下的 Python 包；节点类四要素 `CATEGORY`、`INPUT_TYPES`、`RETURN_TYPES`、`FUNCTION`；包级导出 `NODE_CLASS_MAPPINGS` 即被发现注册；可带 `WEB_DIRECTORY = "./web/js"` 注入前端 JS；无热载需重启。来源：docs.comfy.org/custom-nodes/walkthrough
- ComfyUI-Manager（社区）：安装/发现/评分前端，以 Registry 为后端。来源：github.com/ltdrdata/ComfyUI-Manager
- Comfy Registry（官方）：semver、发布即不可变；workflow JSON 记录节点版本保证可复现；安全上「All nodes will be scanned for malicious behaviour such as custom pip wheels, arbitrary system calls, etc.」。来源：docs.comfy.org/registry/overview
- 分层判定（含推断）：平台本体=执行图引擎+节点加载器+（注册表）；功能面几乎全在节点；custom node 本质是任意 Python + 前端 JS 直接进进程，属安全上最激进的 B 模式。

## 第四章 MCP 标准现状（2026-11）

- **版本**：现行规范为 **2026-07-28**（此前 2025-11-25 引入 URL 模式 elicitation，2025-06-18 引入 elicitation）。来源：modelcontextprotocol.io 规范页
- **Host/Client/Server 分工**（规范原文）：MCP 为「client-host-server architecture where each host can run multiple client instances」；**Host**「creates and manages multiple client instances; controls client connection permissions and lifecycle; enforces security policies and consent requirements; handles user authorization decisions; coordinates AI/LLM integration and sampling; manages context aggregation across clients」；**Client** 与恰好一个 server 1:1；**Server** 通过 primitives 暴露 resources/tools/prompts。协议已改为每请求自包含（stateless，`_meta` 能力协商 + `server/discover` 预发现）
- **基元控制权**：tools=模型控制、resources=应用控制、prompts=用户控制；sampling 由 client 中介；roots 与 elicitation 为反向输入通道
- **桌面应用做 MCP host（Node/Electron）**：官方 TypeScript SDK v2（2026-07-27 发布）拆为 `@modelcontextprotocol/server` 与 `@modelcontextprotocol/client`（v1 `@modelcontextprotocol/sdk` 在 1.x 分支至少维护到 v2 后六个月）；「runs on Node.js, Bun, and Deno」；实现 2026-07-28 规范；schema 用 Standard Schema（Zod v4/Valibot/ArkType）；带 Express/Fastify/Hono/Node HTTP 中间件适配。Electron 主进程即 Node 环境——「ChatGPT 桌面应用（Electron）与 Codex CLI/IDE 共享 MCP 配置」即为 Electron 桌面端做 MCP host 的官方生产先例
- **「MCP 工具 → 流程节点」的先例**（三家做法一致：**连接时拉工具清单，前端动态生成参数面**）：
  - n8n：MCP Client 节点自动取 `tools/list` → 下拉选择 → 参数手填或 JSON
  - Dify：「Connect an MCP server to import its tools into Dify」，**仅支持 HTTP transport**；OAuth 默认开 DCR；也支持把自家应用发布为 MCP server；另有 OpenAPI/Swagger 导入生成工具、Workflow-as-Tool。来源：docs.dify.ai/en/cloud/use-dify/workspace/tools.md
  - 扣子（Coze）：「基于 MCP 服务创建插件」——填 URL（须 HTTPS 域名）+授权 → 「系统将自动同步并添加对应的所有 MCP 工具」「你无需手动添加工具参数，可直接进行试运行」→ 发布后供智能体与工作流使用；反向亦可将工作流/插件发布为 MCP 工具。来源：docs.coze.cn/guides_create_a_plugin_based_on_mcp

## 第五章 操作电脑（computer use）技术路线

### 5.1 模型厂商官方路线（均为「截图+结构化动作+宿主执行」）

- **Anthropic computer use tool**：`computer_toolset_20260801`（Claude 5.5+ 模型，**stable/GA**）——一个 toolset 给 Claude 17 个成员工具（`screenshot`、`left_click`、`type`、`zoom` 等）；**Claude 不直接连机器，宿主应用在自己环境里执行每个调用**；坐标=截图像素；配套 text_editor/bash；参考实现为 Docker 容器（Xvfb+Firefox/LibreOffice）；安全建议：专用 VM/最小权限、网络白名单、不喂凭据、人类确认关键操作、返回截图自动过提示注入分类器。来源：platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool

### 6.3 桌面应用插件机制先例：内核与功能面的分层逻辑

- **VS Code**（A 模式标杆）：扩展运行在**独立 extension host 进程**（「A misbehaving extension cannot impact VS Code」）；惰性激活（activation events）；`extensionKind` 声明运行位置；扩展被禁止改 UI DOM、拖慢主进程。分层逻辑：**能力内核（渲染、编辑器模型、进程隔离、API 面）在本体；功能面在扩展；贡献点静态声明让 UI 在扩展未激活时即可渲染**
- **Raycast**：扩展=TS/React/Node 包 + 内置 UI 组件库，经 Store 分发；「AI Extensions give Raycast AI the ability to take action across your installed extensions…Raycast picks the right tool automatically」——**把已装扩展变成 AI 可调用工具集**（对星丛「节点即 agent 工具」有直接参照意义）。来源：manual.raycast.com/extensions
- **Obsidian**：插件=`manifest.json`+`main.js`+可选 `styles.css`，社区插件走 GitHub 审核；**插件不沙箱、以完整 Electron/Node 权限运行**（多源印证，部分证实）

## 第七章 业界三种模式（客观总结）

### 模式 A：全平台内置（VS Code 内核式）
能力内核+运行时+安全边界全在本体；插件是被宿主严格调度的受限单元（独立进程、静态贡献点、惰性激活、稳定 API 面）；computer use 在两家模型厂商也归入此类。
适用条件：能力间耦合紧、安全与质量须平台兜底、扩展损坏不能伤本体。代价：贡献门槛高、平台开发负担大。

### 模式 B：全生态节点（n8n/ComfyUI 式）
平台=执行引擎+节点加载器+参数 schema 渲染器+注册表/审核；官方能力与社区能力**同构**（n8n 的 MCP/AI Agent 是官方 core 节点但仍是节点）。
适用条件：扩展单元=可组合计算单元、参数可静态/半静态描述、目标用户是流程搭建者、希望生态自供给。代价：版本与安全治理复杂。

### 模式 C：平台内核+生态表面（Claude Code/Codex 式）
**内核**=agent loop、工具执行器、权限/沙箱系统、上下文管理与渐进披露 loader、模型路由；**表面**=全部以用户文件表达：skills（markdown+开放标准 agentskills.io）、agents（markdown）、commands（已并入 skills）、hooks（json）、MCP servers、模型设置。分发层再出现插件/marketplace 打包。
适用条件：产品本质是上下文受限的 agent（渐进披露是硬需求）、扩展内容以知识/流程/prompt 可表达、用户零包管理即可扩展。代价：安全治理依赖目录约定+权限系统；「能力」与「内容」边界需持续维护。

### 混合/边界证据
- Claude Code 把 computer use 实现为**内置 MCP server**：平台内置能力借用生态协议暴露
- n8n 把 MCP/AI 做成**官方 core 节点**：平台新能力以生态单元形态进入
- MCP→节点适配器在 n8n/Dify/扣子三家高度一致：连接时拉工具清单→动态生成参数面
- Office 输出：库层成熟；产品层 HTML 内置、Office 走生态；agent 内普遍「写代码调库」
- computer use：视觉路线+宿主执行+逐应用审批是事实标准

## 八、星丛映射与建议（⚠ 编排者决策建议，非取证内容；对照已封版 00 v1.2 / 01 v1.0 / 02 v1.0）

### 8.1 总判据（一句话）

**执行与安全（沙箱/键鼠/网络白名单/密钥/上下文管理/模型路由）→ 应用本体；可组合的计算与 IO 单元（一次 MCP 调用、一次 Office 生成、一次浏览器/系统操作）→ 节点；知识与流程（skill/命令/prompt）→ 文件级用户内容，由本体 loader 加载、工坊消费。**

即：**本体强化「内核」，节点强化「表面」**——星丛的产品身份（AI 开发节点、节点以 zip 流通、人编排流程）决定了它天然是 B 模式（n8n 同类），而 AI 双工坊的 agent 内核应该按 C 模式（Claude Code/Codex）强化。业界两条混合先例恰好支撑：n8n 把 MCP/AI 做成官方 core 节点（新能力以节点进入）、Claude Code 把 computer use 做成内置 MCP server（内核能力借扩展协议暴露）。

### 8.3 「强化自定义节点 vs 强化应用本体」的直接回答

**不是二选一，是按层切：**
1. **强化应用本体（内核层）**——MCP host、computer use 执行器、模型路由、skill loader、权限沙箱、工坊 agent loop。理由：全部是「执行与安全」能力，业界无一例外平台内置；下放给节点脚本会击穿 02 §12 的沙箱白名单与权限类目体系。
2. **强化节点（表面层）**——每项内核能力都收敛为一个**平台内置节点**（mcp.call / computer.* / office.* / html.report / ai.subagent），与 12 个既有平台节点同注册表同 N1~N8 模型；AI 现场开发的自定义节点通过 **ctx 能力集**消费这些内核（ctx.file 已冻结、llm 多模态已进 V1）。理由：星丛的统一扩展单元就是节点（n8n 先例：新能力以官方 core 节点进入，不另起插件体系）；节点可上广场流通，内核不可流通。
3. **不新建第三体系**——不做独立的「命令系统」「插件系统」（VS Code 式扩展 API）。业界 2025-2026 的收敛信号非常明确：Claude Code/Codex 都把 commands 并入 skills、Codex 移除了 MCP server 模式、n8n 把 MCP/AI 收敛为节点。星丛已有的「节点资产包+广场+工坊」三件套就是它的插件体系，扩 capacity 时往这套里加，不开新口子。
