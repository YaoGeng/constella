### 1.3 数据模型与 Prisma 组织（事实）

来源：`prisma/schema.prisma`、`prisma/models/auth/*.prisma`、`prisma.config.ts`

- 采用 **Prisma v7 新范式**：`prisma.config.ts` 统一配置 + driver adapter（`@prisma/adapter-pg`）直连 + **多文件 schema**（`prisma/models/` 递归扫描）+ 新 generator `prisma-client`（输出到 `generated/prisma`）。
- 数据模型仅两张表：
  - `User`（id UUID、email unique、passwordHash、时间戳）
  - `RefreshToken`（tokenHash SHA256、userId 级联删除、expiresAt，tokenHash/userId 各有索引）
- **无初始 migration 文件**（树中 `prisma/migrations/` 为空目录，README 目录结构图中有该目录但无内容）。

### 1.4 路由/中间件/校验/错误处理组织（事实）

来源：`src/` 全部源码，逐文件读取

- 组织方式：`routes/index.ts` 聚合子路由 → 每模块 `模块名/模块名.routes.ts + .schemas.ts + .middleware.ts`，模式清晰，新增业务模块（如节点包、市场）可按此扩展。
- 认证实现质量高于一般模板：
  - JWT 用 Hono 内置 `hono/jwt` 中间件（HS256），Access Token 15 分钟；
  - Refresh Token 为随机 UUID 拼接（非 JWT），**SHA256 哈希落库、一次性轮换**（refresh 即删旧发新）；
  - 登录含 dummy bcrypt compare 防时序攻击；env 变量经 Zod 全量校验（JWT_SECRET 最短 32 位）。
- **错误处理是弱点**：无全局 `app.onError`、无 404 处理器、无统一错误码结构；handler 内手写 `c.json({error: ...}, 4xx)`；「异常捕获」仅指进程级 SIGTERM/SIGINT/uncaughtException（README 如此宣称，与代码一致）。
- 环境分层：`.env.{dev|test|prod}` 优先加载，`APP_ENV` 映射 `NODE_ENV`。

### 1.5 README 宣称 vs 实际核对（事实）

README 宣称：认证体系、TS strict、Zod v4 校验、ESLint+Prettier、JSON 结构化日志（零依赖）、Prisma v7、优雅关闭。**逐项与源码核对全部属实，无夸大。** API 仅 4 个端点：`POST /auth/register|login|refresh`、`GET /user/profile`。

### 1.6 作为星丛 server 的结论

**优点（可直接复用的部分）**：账号体系（注册/登录/令牌轮换/受保护路由示例）、技术栈与约束完全匹配（Hono 4 + Prisma 7 + PG + Zod 4 + TS strict）、模块化路由/校验/配置分层模式可直接套用到新业务域。

**缺口（需自建，按星丛四域拆解）**：

| 星丛需求 | 模板现状 | 需自建 |
|---|---|---|
| 广场/市场 | 无 | 列表/分页/排序/搜索（需接 PostgreSQL 全文检索或外部搜索引擎）、收藏/点赞、版本发布流 |
| 节点包托管 | 无 | 文件上传 API、对象存储（S3/R2/MinIO，Node 生态 `@aws-sdk/client-s3`）、语义化版本与包元数据模型、下载计数 |
| 账号 | 有基础认证 | 邮箱验证/找回密码、第三方 OAuth、RBAC（模型无 role 字段）、用户资料 |
| 审核 | 无 | 审核状态机（模型无 status 字段）、管理员角色、审核操作记录、举报 |

### 2.3 推荐（已采纳）

**推荐 @xyflow/react v12**。针对星丛的判定逻辑：星丛节点是深色玻璃拟态卡片（backdrop-blur、CSS tokens）→ 只有 DOM 渲染方案（xyflow/手写）能无损承载，xyflow 相对手写省掉全部交互基建；true/false 双出口 = 原生 multi-handle 模式；运行态连线动画 = `animated` + 自定义 edge 的 SVG path；数百节点 = 官方压力测试覆盖量级；MiniMap/Controls 开箱即用。**唯一需自建的是撤销重做**（zustand + zundo，官方讨论区认可模式，成本可控）。**与用户拍板的 Zapier/n8n 同款方向一致：Zapier 画布即 React Flow 构建，n8n 为其 Vue 生态移植（vue-flow）。**

- 版本与兼容见第四章（6.7.0 / React 19 原生）。**不建议 C 端复用**：antd 是 CSS-in-JS + 自有类名体系（v6 默认启用 CSS 变量但机制不变），与 Tailwind 并行会形成双样式系统；其设计语言面向企业中后台（此为定性判断），与高定制玻璃拟态 C 端调性冲突——高度定制时等于与组件库内部 DOM 结构对抗（v6 迁移文档自己警告「组件内部 DOM 结构调整可能破坏自定义选择器」）。antd 6 留在管理端（约束已冻结），C 端与管理端共用 design tokens 而非共用组件库。

**Headless UI（@headlessui/react）**
- latest 2.2.10（**2026-04-07**，约 7 个月未更新）；peer `react ^18 || ^19 || 19.0.0-rc`（React 19 支持自 2.2.0 起即声明）；周下载 996 万。Tailwind 官方团队出品。**官网确认仅 16 个组件：无 Drawer、无 Toast、无 Slider**——demo 7 件套缺 3，需拼装第三方（Sonner 等），作为唯一组件库不成立。

### 3.2 对比表（权重 × 0~4 分）

权重：Tailwind 原生程度 0.25，React 19 与稳定性 0.15，玻璃拟态自由度 0.25，demo 组件覆盖 0.20，Electron 兼容 0.05，维护与社区 0.10

### 3.3 推荐

**推荐 shadcn/ui**：所有维度 4 分，为帕累托占优解——权重怎么调排序不变，结论稳健。对星丛的具体优势：组件源码即 Tailwind 类 + CSS 变量，玻璃拟态 design tokens 直接落 `globals.css`；demo 7 件套全覆盖；copy-in 模式天然免疫「库停更/破坏性升级」（源码在自己仓库）；且与画布层同生态——xyflow 官方的 React Flow UI 组件库即基于 shadcn CLI 体系，节点卡片与面板组件可复用同一套代码风格。
**备选 Ark UI**：若团队不接受源码复制模式（评审/升级偏好 npm 锁版本），Ark UI 是 headless 里最活跃且覆盖全的选择，代价是 7 件套的样式全部从零写（demo tokens 迁移工作量大于 shadcn）。
**Base UI 观察**：设计理念与 MUI 团队投入均优，但 1.0 stable 一年未落地，TDD 阶段不建议押注。
